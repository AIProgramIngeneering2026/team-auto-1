| Карта | Ответ контракта |
|---|---|
| **К1 Двойной клик** | Обязательный `Idempotency-Key`, уникальный индекс в БД. Повтор с тем же ключом и телом возвращает `200` с прежним `id`, новый Job не создаётся — [openapi.yaml, POST /notifications](../api/openapi.yaml), [ADR-0002](https://github.com/AIProgramIngeneering2026/team-auto-1/blob/main/docs/ADR/0002-idempotency-key.md). |
| **К2 Ответ потерялся** | Клиент повторяет запрос с тем же `Idempotency-Key` и телом. Сервис возвращает `200` с прежним Job. Повторная отправка не выполняется — [ADR-0002](https://github.com/AIProgramIngeneering2026/team-auto-1/blob/main/docs/ADR/0002-idempotency-key.md). |
| **К3 Неизвестная операция** | Неизвестный канал отклоняется с `400 unknown_channel`, Job не создаётся — [openapi.yaml, POST /notifications](../api/openapi.yaml). |
| **К4 Кривые параметры** | Некорректные параметры отклоняются до создания Job с `400 invalid_params` и указанием ошибочного поля в `details`; некорректный JSON — `400 bad_request` — [openapi.yaml, POST /notifications](../api/openapi.yaml). |
| **К5 Воскрешение** | Повторный запуск завершённого Job не поддерживается. Терминальные состояния неизменяемы. Для повторной отправки создаётся новый Job с новым `Idempotency-Key` — [ADR-0001](https://github.com/AIProgramIngeneering2026/team-auto-1/blob/main/docs/ADR/0001-background-dispatch.md), раздел «Решение». |
| **К6 Отмена** | Отмена поддерживается только в состоянии `accepted`. Успешная отмена возвращает `200` и `cancelled`; если отправка уже началась — `409 cannot_cancel`. Гонка между отменой и запуском отправки разрешается условным SQL UPDATE — [ADR-0001](https://github.com/AIProgramIngeneering2026/team-auto-1/blob/main/docs/ADR/0001-background-dispatch.md). |
| **К7 Огромный вход** | Общий лимит входящего потока и размера очереди в v1 не предусмотрен. При росте нагрузки очередь Job увеличивается, задержка доставки растёт. Устойчивость к увеличению входа в 1000 раз сознательно не гарантируется — [ADR-0001](https://github.com/AIProgramIngeneering2026/team-auto-1/blob/main/docs/ADR/0001-background-dispatch.md), раздел «Цена решения». |
| **К8 Чужой или несуществующий id** | Несуществующий Job возвращает `404 notification_not_found`. Аутентификация и разделение Job по клиентам в v1 не предусмотрены: любой клиент, знающий ID, может получить информацию о Job — [ADR-0002](https://github.com/AIProgramIngeneering2026/team-auto-1/blob/main/docs/ADR/0002-idempotency-key.md), раздел «Контекст и ограничения». |
| **К9 Перезапуск сервера** | При старте сервиса Job в состоянии `sending` переводятся в `undelivered` с `error = interrupted`. Гарантия доставки — не меньше одного раза; при ручном повторе возможен дубль — [ADR-0001](https://github.com/AIProgramIngeneering2026/team-auto-1/blob/main/docs/ADR/0001-background-dispatch.md). |
| **К10 Внешний сервис** | Временные ошибки приводят к повторным попыткам (максимум 3), постоянные ошибки получателя — к `undelivered` без повторов. В v1 используется заглушка провайдера — [ADR-0001](https://github.com/AIProgramIngeneering2026/team-auto-1/blob/main/docs/ADR/0001-background-dispatch.md), раздел «Контекст и ограничения», [tool-contract.md](../tool-contract.md). |


## Что предложил ИИ

### Промпт

Модели были предоставлены OpenAPI-контракт сервиса (`docs/api/openapi.yaml`), архитектурные решения (`docs/ADR/0001-background-dispatch.md`, `docs/ADR/0002-idempotency-key.md`), контракт Tool (`docs/tool-contract.md`) и колода покера К1–К10.

Использованный промпт:

> Выступи в роли атакующего при проверке API-контракта.
>
> Изучи предоставленный OpenAPI-контракт, ADR и колоду покера К1–К10.
>
> Найди ещё 3 ситуации, на которые контракт не даёт однозначного ответа. Не повторяй сценарии существующих карт.
>
> Для каждой ситуации укажи:
> 1. Сценарий атаки.
> 2. Что именно не определено контрактом.
> 3. Возможные последствия.
> 4. Какое изменение в контракт или ADR ты предлагаешь.
>
> Выбирай реалистичные сценарии, связанные с безопасностью, надёжностью и производительностью сервиса.

### Найденные ситуации

#### 1. SSRF через webhook

**Сценарий:** клиент создаёт уведомление с каналом `webhook` и указывает URL внутреннего сервиса, например `http://localhost:8080/admin` или адрес из диапазона `169.254.0.0/16`.

**Проблема:** контракт предусматривает передачу URL для webhook, но не определяет ограничения на адреса назначения. Злоумышленник может попытаться заставить сервис обращаться к внутренним ресурсам инфраструктуры.

**Решение: Приняли.**

Добавить в контракт требования безопасности для webhook:
- Разрешить только HTTPS.
- Запретить loopback, private и link-local IP-адреса.
- Проверять адрес после DNS-разрешения.
- Запретить автоматическое следование редиректам либо проверять адрес назначения каждого редиректа.

#### 2. Шторм повторных попыток

**Сценарий:** внешний провайдер несколько минут недоступен, после чего восстанавливает работу. Большое количество Job одновременно начинает повторные попытки отправки.

**Проблема:** контракт определяет максимум три попытки, но не устанавливает конкретную стратегию задержек между ними. Одновременные повторы могут создать дополнительную нагрузку на восстановившийся провайдер.

**Решение: Приняли.**

Дополнить контракт стратегией повторных попыток:
- Использовать экспоненциальную задержку между попытками.
- Добавить случайный разброс задержки (jitter).
- Учитывать `Retry-After`, если провайдер возвращает этот заголовок.
- Сохранить ограничение в три попытки.

#### 3. Чрезмерный опрос статуса Job

**Сценарий:** клиент начинает опрашивать `GET /notifications/{id}` каждые 10 мс для каждого созданного задания.

**Проблема:** контракт не определяет ограничений частоты запросов на получение статуса. При большом количестве клиентов частые запросы могут создать избыточную нагрузку на PostgreSQL и замедлить работу API и Dispatcher.

**Решение: Не приняли для v1.**

В текущей версии нет ограничения входящего потока запросов. Введение отдельного rate limit для получения статусов увеличит сложность реализации. При этом текущая архитектура рассчитана на небольшую нагрузку.

Вопрос производительности оставляем в качестве ограничения первой версии. При появлении проблем с нагрузкой введём ограничение частоты запросов и ответ `429 Too Many Requests`.
