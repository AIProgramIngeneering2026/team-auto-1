# ADR-0001. Отправка выполняется в фоне: ответ `202` и Dispatcher в том же процессе

## Контекст и ограничения

Отправка может занять секунды: у канала есть таймаут, при неудаче до 3 попыток, плюс ограничитель трафика под лимиты
провайдеров. Сценарий С1 требует, чтобы `POST /notifications` отвечал `202` с `id`, а статус клиент смотрел через С2.
Отмена (С3) и запуск отправки не должны оба «победить» одновременно.

Ограничения: команда небольшая, Docker Compose поднимает сервис, PostgreSQL и заглушку провайдера. Брокеры сообщений
(Kafka, RabbitMQ) на оценку не влияют (`project.md`).

## Решение

1. `POST /notifications` проверяет вход, записывает Job в состоянии «принято» и сразу отвечает `202`. Провайдера он не вызывает.
2. Отправку выполняет фоновый воркер Dispatcher **в том же процессе**, что и API. Очередью служит сама таблица Job:
   воркер периодически выбирает Job в состоянии «принято».
3. Переход «принято → отправляется» и отмена «принято → отменено» делаются **условным обновлением** одной SQL-командой
   (`UPDATE … SET status = … WHERE id = ? AND status = 'accepted'`). Выигрывает ровно одна из двух команд,
   проигравший получает `409 cannot_cancel` (отмена) или пропускает Job (воркер). Это закрывает гонку из С3.
4. При старте сервиса Job в состоянии «отправляется» переводятся в «не доставлено» с `error = interrupted`
   (правило из `requirements.md`).
5. Гарантия доставки: **не меньше одного раза**. Если сервис упал после фактической отправки, но до записи «доставлено»,
   при ручном повторе возможен дубль. «Ровно один раз» не обещаем.

## Рассмотренные альтернативы

1. **Синхронная отправка внутри запроса** (ответ после доставки). Проще, но запрос висит до 3 попыток × таймаут;
   обрыв соединения клиента оставляет неизвестность, что с сообщением; ограничить трафик под лимиты провайдера нельзя.
2. **Брокер сообщений** (RabbitMQ, Kafka). Лучше масштабируется и надёжнее доставляет задачи, но это ещё один сервис
   в Compose, ещё одна точка отказа и настройка, а выигрыша в оценке нет.
3. **Очередь в памяти процесса.** Просто, но при перезапуске теряет все принятые, ещё не отправленные Job.
4. **Отдельный процесс-воркер.** Чище масштабируется, но два артефакта запуска и две конфигурации ради нагрузки, которой в v1 нет.

## Цена решения

- Доставка начинается с задержкой до интервала опроса таблицы (порядка секунды).
- Опрос создаёт постоянную нагрузку на БД; нужен индекс по состоянию Job.
- Клиент узнаёт результат только опросом `GET /notifications/{id}`, уведомления о результате в v1 нет.
- При падении процесса возможны `interrupted` и дубль при ручном повторе (см. пункт 5 решения).
- API и воркер делят ресурсы одного процесса: тяжёлая отправка может замедлить ответы API.
- Отмена возможна только в состоянии «принято»: после начала отправки сообщение отозвать нельзя, клиент получает
  `409 cannot_cancel`. Отмену «на лету» и откат уже выполненных попыток сознательно не поддерживаем.
- Входящий поток клиентов в v1 не ограничивается: лимитов на клиента нет, ограничитель трафика сдерживает только
  исходящие вызовы провайдеров. При росте входа в разы растёт очередь Job в «принято» и задержка доставки; пока БД
  выдерживает, API продолжает отвечать `202`. Устойчивость к входу «в 1000 раз больше обычного» сознательно не гарантируем.

## Условия пересмотра

- Измеренная нагрузка опроса на PostgreSQL или задержка старта отправки перестают укладываться в требования.
- Клиенты начинают присылать больше, чем сервис успевает отправлять. Тогда вводим лимит запросов на клиента (`429`)
  и предельный размер очереди «принято».
- Воркеры нужно масштабировать независимо от API. Тогда выносим тот же код в отдельный процесс на той же таблице:
  условное обновление уже безопасно для нескольких воркеров. Если и этого мало, вводим брокер.
- Требование «ровно один раз» от клиентов: потребуется подтверждение приёма на стороне провайдера и другая схема хранения.
